# The test suites

The pipeline runs this repository's suites. Its part `suite-selection`, switched on in `.github/ci-config.yml`, selects in its job `suite-selection` the entry files that a change reaches from the suite list `tests/suites.json`; the shared workflow `suite-jobs.yml` runs the Linux entry files in shards and the Windows entry files in one job, on the runners that the suite list's `jobs` states, `ubuntu-26.04` and `windows-2025`, each entry file under the recording step. This file says which suites there are, how a suite is added, removed and kept in step with what it reads, and how an entry file runs locally with the tools its cases need. "Suite list" and "Job layout" in `docs/maintaining.md` document the suite-list format, the selection rules and the jobs; this file points to them and does not repeat them.

## The suites in `tests/suites.json`

A suite is one item of `suites` in `tests/suites.json`. It states its name, its entry files, its `command`, the `setups` it needs, a duration estimate per entry file in `entry_durations`, and its stored path list with any directory memberships, existence reads, lookup directories and extra reads. A Windows suite states `"os": "windows"`; `windows` and `etw-consumer-build` are such suites. The `always` list is empty.

A suite names its entry files in `entries` by one glob pattern or by path, as the Tests principle in `docs/agents/ci.md` states. Nine suites share a name rule and name their entry files by its pattern: `ci-policy` (`tests/test_ci_policy_*.py`), `dependabot-auto-merge` (`tests/test_dependabot_auto_merge*.py`), `consumer-kit-templates` (`tests/test_consumer_kit_*.py`), `suite-selection` (`tests/test_suite_selection*.py`), `hygiene` (`tests/test_hygiene_*.py`), `python-tests` (`tests/test_python_tests*.py`), `pipeline` (`tests/test_pipeline_*.py`), `sync` (`tests/test_sync_*.py`) and `publication-checks` (`tests/test_publication_*.py`). Each pattern matches every entry file of its suite and no tracked file that is no entry file of that suite, so an entry file takes the prefix of the suite it belongs to and of no other. The suites with one entry file name it by path: `pinned-tools`, `pinned-tools-windows`, `python-language-step`, `python-floor`, `dotnet-test`, `node-test` and `etw-consumer-build`. `windows` names its two entry files by path, `tests/test_windows_recording.py` and `tests/test_suite_selection_recording_setups.py`: the second is also an entry file of `suite-selection`, so the two share no name rule.

`tests/test_ci_policy_entry_files.py` fails when a tracked file that the pattern `tests/test_*.py` matches is no entry file of any suite, named by path or matched by a pattern, and its message names each such file. A helper or a fixture module therefore has a name that the pattern does not match.

Every entry file runs as its own process with its suite's `command` followed by the entry file's path: `python3 -m unittest -v <entry file>` for the Linux suites and `python -m unittest -v <entry file>` for `windows` and `etw-consumer-build`. A suite job installs the tools of its setups with pinned actions, runs the setups that record nothing (`python`, `node` and `dotnet`, which are tool setups) before the recording starts, runs the other setups under the recording, then runs its entry files two at a time and the recording's `check`. The setups are the named items of the top-level `setups` of `tests/suites.json`, each with one script under `tests/setups/`: `actionlint`, `zizmor`, `reuse`, `ruff` and `mypy` run `tests/setups/pinned-tool.sh`, and `commitlint` runs `tests/setups/commitlint.sh`. An entry file that needs a setup the rest of its suite does not, such as a hygiene entry file that needs `actionlint`, states it in `entry_setups`. Gitleaks is no setup of `tests/suites.json`: the configuration file names it under `pinned-tools`, so the suite jobs install it at the version of `actions/repository-hygiene/pins.json` outside the recording, and `tests/test_hygiene_gitleaks.py` states it in `entry_setups` as a pinned tool.

Several suites are selected per entry file (`entry_selection`), among them `ci-policy`, `hygiene`, `publication-checks` and `suite-selection`. Each entry file has its own stored list (`entry_paths`), and a change starts only the entry files whose own lists it reaches. `entry_extra_paths` and `entry_directory_memberships` record reads that apply to only some entry files.

`ci-policy` (`tests/test_ci_policy_*.py`) is the light suite: it reads tracked files in its own process, with no tool installation, no network and no fixture Git repository, and holds the checks over every workflow and over the shared surface of `actions/`. Each part's suite parses the invocations of its scripts in its shared workflows with the scripts' own parsers (`tests/workflow_commands.py`), so a change to a part's workflow runs `ci-policy` and that part's suite. `ConsumerPathTests` in `tests/test_ci_policy_pipeline.py` holds the `run:` blocks and step environments of `pipeline.yml`, `repository-hygiene.yml`, `suite-selection.yml`, `suite-verdict.yml` and `python-tests.yml`: every path of this repository that a block gives a program starts with a variable that a step sets through `$/`, and the definitions of `hygiene.py changes` (`--definition`, `--packages-definition` and `--markdown-definition`) are the one exception. `FixturePartPathsTests` in `tests/test_ci_policy_pipeline_parts.py` holds the `paths` of each project part in `.github/ci-config.yml` complete: each names its fixture folder, every part folder that the part's job loads through `$/`, `actions/pipeline/`, `.github/workflows/pipeline.yml` and `.github/workflows/ci.yml`. The link check over this checkout's Markdown is a check of the hygiene caller, not of the suite jobs; its cases on fixture Markdown are `tests/test_hygiene_link_check.py` in the `hygiene` suite.

The first Linux shard also runs the Python language step outside the recording: ruff with the rule sets `F` and `E9` of `ruff.toml`, without mypy. The `python-floor` suite checks the shared Python code against Python 3.12.

The `python-tests` suite (`tests/test_python_tests.py`, `tests/test_python_tests_workflow.py`) runs the script of Python tests on fixture repositories and projects in temporary directories, with a virtual environment without pip as the consumer's Python and stand-ins for pip and pytest on its `PYTHONPATH`, so it installs no package and needs only Python and Git. The fixture project `tests/fixtures/python_tests` is no input of a suite: `python-tests-caller.yml` runs the shared workflow on it.

The `pipeline` suite (`tests/test_pipeline_*.py`) runs the plan program of the pipeline, `actions/pipeline/plan.py`, on fixture consumers in temporary Git repositories and on fixture schema folders with invented parts (`tests/pipeline_fixtures.py`), and checks the real schema folder; it needs only Python and Git. `tests/test_pipeline_custom.py` runs the plan on the free job's setups in the real schema and runs the command of the job's last step in Bash on the fixture scripts `tests/fixtures/custom/`; those cases skip without `bash`. `tests/test_pipeline_steps_shell.py` runs the shell of the pipeline's steps in Bash on a fixture consumer, a temporary Git repository that holds no file of this repository: the plan step with its base and head, the tool installation, the Gitleaks step with and without `.gitleaks.toml`, and the install and test steps of `python-verify` and `python-test`; it skips without `bash` and on Windows. `tests/test_pipeline_schema.py` holds the two exclusions of repository hygiene in the real schema and `plan.py setting`, which reads them, and `tests/test_pipeline_workflow.py` runs the steps `coverage` and `links` of the pipeline's hygiene job in Bash on fixture consumers with and without those exclusions; those cases, like the run of the plan step, skip on Windows and without `bash` and `python3`. Its entry files `tests/test_pipeline_callers.py`, `tests/test_pipeline_register.py` and `tests/test_pipeline_dependabot.py` run the consumer checks, `actions/pipeline/consumer_checks.py`, on a fixture consumer with a fixture consumer kit of invented templates and a local HTTP server that stands in for the GitHub API (`tests/consumer_checks_fixtures.py`). `tests/test_pipeline_register.py` also holds the switch-over check, for an entry of the register and for the free job's request, on the invented parts of the fixture schema folder, and `tests/test_pipeline_callers.py` the comparison of the CI guide, also for a fixture consumer that holds the files of the real consumer kit. The form of the catalogue, its decision rule and the paths it names are `tests/test_ci_policy_catalogue.py` in `ci-policy`, and the template of the CI guide is checked in `tests/test_consumer_kit_fixed_callers.py`. Its entry file `tests/test_pipeline_release.py` runs the release program, `actions/pipeline/release.py`, on a fixture consumer with fixture tags that it signs with SSH keys of its own (`tests/release_fixtures.py`), runs the commands of the job that collects the files in Bash, and publishes against a local HTTP server that stands in for the GitHub API, which also holds the tags, the files of a commit, the repository's releases and owner, and the generated release notes that the publishing reads; the cases that sign skip without `ssh-keygen` and those that run the job's commands without `bash`. The contract of `release.yml`, of the caller `release-caller.yml` and of the template's rights is `tests/test_ci_policy_release.py` in `ci-policy`. The contract of `pipeline.yml` and of the caller `ci.yml` is `tests/test_ci_policy_pipeline.py` in `ci-policy`, and that of the templates of the fixed callers `tests/test_ci_policy_fixed_callers.py`; `tests/test_consumer_kit_fixed_callers.py` in `consumer-kit-templates` holds the kit's templates and README. `tests/test_pipeline_parts.py` checks the projects and settings of the project parts in the real schema, the runner labels it accepts, and the pipeline's invocations of their scripts; the contract of their jobs, and the count of the reusable workflows that the pipeline reaches, is `tests/test_ci_policy_pipeline_parts.py` in `ci-policy`. Each of the two entry files holds the project parts in one register, `PARTS`, so a new part is one entry in each.

The promotion of `v1` has its program tests in `tests/test_hygiene_v1_promotion.py`: the decision by promotion class and the leased tag push run on fixture repositories in temporary directories, the deploy-key setup of those pushes runs with the function that pushes replaced, the CI on `main` is read from a stand-in for the GitHub API, and the read and the write of the management repository's caller and the start of the sync go to a stand-in for the `gh` CLI. `tests/test_ci_policy_shared_surface.py` holds the promotion class of every path of the shared surface, and `tests/test_ci_policy_hygiene_promotion.py` the contract of `promote-v1.yml`.

The `dotnet-test` suite (`tests/test_dotnet_test.py`) starts the script of the part `dotnet-test` on a fixture repository in a temporary directory, with a stand-in for the `dotnet` command first on `PATH` that writes the TRX reports of a test run and ends `dotnet run` with the exit code of a console test program, so it builds nothing, restores no package and needs only Python. The fixture projects `tests/fixtures/dotnet_test` and `tests/fixtures/dotnet_console`, a console test program, are no input of a suite: `ci.yml` runs the part `dotnet-test` on them, the second with `console-runner`, and the parts `python-verify` and `python-test` on `tests/fixtures/python_tests`.

The `node-test` suite (`tests/test_node_test.py`) starts the script of the part `node-test` on a fixture repository in a temporary directory, with stand-ins for the `node` and `npm` commands first on `PATH` that record each command, report a Node version of the test's choice and the npm version that the last `npm install --global npm@<version>` installed, so it installs nothing and needs only Python. The fixture project `tests/fixtures/node_test` is no input of a suite: `ci.yml` runs the part `node-test` on it.

The `pinned-tools` suite (`tests/test_suite_jobs_pinned_tools.py`, Linux) and the `pinned-tools-windows` suite (the same entry file, on Windows) state the setups `python` and `gitleaks` and the extra path `actions/repository-hygiene/pins.json`. The entry file runs the pinned Gitleaks that its suite job installed, compares its version with the pins file and fails when they differ. It skips unless `GITHUB_ACTIONS` is `true` and `RUNNER_TEMP` is set, as on a hosted runner. The pinned Node.js has no entry file of its own here, since this repository's suite list holds setups with `tool: node`: `tests/test_suite_selection_recording_setups.py` runs the steps of the Linux suite job around its setups in Bash, and the step of the Windows suite job that names its setups in PowerShell, with a stand-in for the Node.js that the job's action installs, and `tests/test_pipeline_schema.py` holds the setting `pinned-tools` in the real schema.

The automation workflow, `automation.yml`, has its contract in `ci-policy`: `tests/test_ci_policy_automation.py` holds the job-level conditions of its parts, the events of its plan, the two properties of the additions job and what the fixed caller and `automation-caller.yml` give it, `tests/test_ci_policy_additions.py` the additions job beside the rebuild workflow, and `tests/test_ci_policy_full_recording.py` the jobs of the full recording. In the `pipeline` suite, `tests/test_pipeline_automation_invocations.py` parses the workflow's invocations with the programs' own parsers and runs the plan of the workflow's parts on fixture consumers, and `tests/test_pipeline_issue_title.py` starts the issue-title program, `actions/issue-title/issue_title.py`, on fixture events, an invented category file and fixture component folders, with a local HTTP server that stands in for the GitHub API; both need only Python and Git.

The `sync` suite (`tests/test_sync_*.py`) runs the sync program, `actions/sync/sync.py`, against a local HTTP server that stands in for the GitHub API (`tests/sync_fixtures.py`): it holds fixture repositories with their Git objects, refs, pull requests, issues, rulesets and merge settings, answers the App's installation and the auto-merge mutation, refuses a change of settings or rulesets to the App's token, and records every request that writes. The kit is a fixture kit of invented templates and the schema a fixture schema folder; the ruleset template and the merge settings are the real ones. It needs only Python and Git. The contract of `sync.yml` is `tests/test_ci_policy_sync.py` in `ci-policy`, which also holds the sync caller `actions/sync/caller.yml` against the shared workflow, the sync App's permissions and the environment's names in `docs/maintaining.md` against the workflow, and the settings that the sync keeps against the documents that state them: the merge settings and the one required check in the consumer kit of repository hygiene, and no kit that sends a difference of either to a repository's recorded choices.

### Adding a suite

A new suite is one item in `tests/suites.json` with `name`, `entries`, `command`, `setups`, `os` for a Windows suite, and `entry_selection` for a suite selected per entry file. It has no `paths` at first, so it runs on every change. The recording `check` of its first run names its reads as additions; apply them with `recording.py apply`, as "Validation" in `docs/maintaining.md` says, in the change that adds the suite. A setup that no suite has yet is added to the top-level `setups` of `tests/suites.json`, with its script under `tests/setups/`; the suite jobs of `suite-jobs.yml` read it from there, so no workflow file changes for it.

A tool that a suite needs and that is `node` or `gitleaks` is a pinned tool of the configuration file instead: the suite states it under `setups` or `entry_setups` as any other setup, and the top-level `setups` of `tests/suites.json` defines no setup of that name. "Pinned tools" in `docs/maintaining.md` describes them.

A new entry file in a suite that names its entry files by pattern is a tracked file that the pattern matches: it is an entry file from the push that adds it, and no line of `entries` changes. In a suite that names its entry files by path, it joins that suite's `entries`. Either way it gets its own list from the additions of its first run.

### Listing tracked paths

A test lists tracked paths with `git ls-files` and a pathspec of what its result depends on, such as the paths it checks or the patterns of the files it looks for, from the repository root and without Git's own options such as `-C`. It lists every tracked path only when its result depends on the whole tracked set. "Recording step" in `docs/maintaining.md` says which reads the recording takes from each pathspec.

### Removing a suite

A suite leaves `tests/suites.json` with its entry files, unless another suite names them. A setup that no other suite states leaves the top-level `setups` of `tests/suites.json`, with its script.

## Recording-step tests

The entry files of the recording step, `tests/test_suite_selection_recording_*.py` in the `suite-selection` suite, start no tracer and run under the recording like every other entry file. The classification rules run on stored strace recordings and on recorded neutral ETW event files; the wiring and full-recording tests run against the stand-in `strace` of `tests/strace_stand_in.py`, which `RecordingFixture` in `tests/recording_fixtures.py` puts first on the fixture's `PATH`. A new command of these tests belongs to a `StoredFixture` and needs a stored trace; "Renew the stored strace recordings" in `docs/maintaining.md` describes the stored files and their regeneration script. The live ETW cases of `tests/test_windows_recording.py`, the attribution of two entry files that run at the same time included, run under the Windows job's own ETW session.

`tests/test_suite_selection_recording_setups.py` runs the `setups` command of the recording step as its own processes on a fixture repository: the order of the setups before the recording and under it, what each script gets, and what an entry file sees of what they provide; its class `PinnedToolTests` covers the `--pinned` directories of the pinned tools. `tests/test_suite_selection_setups.py` (the `suite-selection` suite, class `PinnedToolTests` for the pinned tools) checks what the suite list accepts for `setups` and `jobs`, what `select` gives the suite jobs, the pinned tools that the configuration file names with the errors of their names, and what a change to a setup selects.

## Windows suite

The Windows suite is `tests/test_windows_recording.py`, run by the `windows` job of `suite-jobs.yml` on `windows-2025` under the ETW recording; the pipeline reports that job as `ci / suite-selection-jobs / windows`. It covers the recording step on Windows. Each entry file gets the `TEMP` and `TMP` that the recording's `exec` gives it: a temporary directory of its own under the recording's output directory in `$RUNNER_TEMP`.

## ETW consumer build suite

The `etw-consumer-build` suite is `tests/test_etw_consumer_build.py`: it rebuilds the ETW consumer of the recording step from its source with the pinned .NET SDK and fails when the result differs from the committed build in `actions/recording/etw-consumer/build/`. It runs in the `windows` job of `suite-jobs.yml` after the `dotnet` setup. Its rebuild test skips without `dotnet` on `PATH` or off Windows; its test of the `dotnet publish` command line runs everywhere, with `subprocess.run` replaced. Its extra read is the SDK pin `global.json`, which the setup reads outside the recording; the configuration files that the build probes in the project's directory and above come from the .NET probe rules of the recording step.

## Running the suites

CI is the only gate, and no local copy of the CI's selection runs before a push. While building, run the entry files of the changed behaviour, each with its suite's `command` from `tests/suites.json`, from the repository root. Python commands set `PYTHONPYCACHEPREFIX` to an external cache directory. The Windows suites run on Windows with `python -m unittest -v <entry file>`.

```text
python3 -m unittest -v tests/test_suite_selection.py
```

The `-v` output of a `python -m unittest` entry file lists every skipped case with its reason.

### Tools the suites need

The suites need Python, and selected publication entry files need Node.js and npm. Selected hygiene and publication entry files also need tools that a checkout does not contain, and selected consumer-kit entry files need Bash:

- Hygiene (`hygiene`). Only the actionlint, zizmor, Gitleaks and REUSE entry files need installed executables; the actionlint entry file also needs ShellCheck. Other hygiene entry files use repository files, Git or fixture archives. Those entry files take tools from `HYGIENE_TOOLS` when set, otherwise from `PATH`, and skip when a required executable is missing. Install the pinned versions for the platform, `windows-x64` or `linux-x64`, into an empty directory outside the repository, and set `HYGIENE_TOOLS` to it:

  ```text
  python actions/repository-hygiene/install_tools.py --pins actions/repository-hygiene/pins.json --platform <platform> --destination <directory>
  ```

  Without `--platform` the installer takes the platform of the machine. In a suite job, Gitleaks is a pinned tool that the job installs itself, so no setup of the suite list installs it there.

- Consumer kit templates (`consumer-kit-templates`). The run cases of `tests/test_consumer_kit_automation_additions.py` and `tests/test_consumer_kit_automation_full_recording.py` run the shell steps of the additions jobs and of the full recording's closing job in `automation.yml` with Bash against a fixture repository, a local remote and a stand-in `gh`; they need Bash, those of the additions jobs also `jq`, and skip on Windows. The cases of the additions jobs run the steps as a consumer with its own suite list runs them, and then with this repository's suite list beside the plan, push and comment steps of `rebuild-etw-consumer.yml`: which of the two automatic routes acts on a failed run, their bounds, their pushes onto a branch that moved, and the rebuild workflow's comment.
- Publication checks (`publication-checks`). `tests/test_publication_references.py` runs the reference check on fixture repositories against a local HTTP server that stands in for the owner's public repository list, and needs only Node.js and Git. The two commitlint cases skip unless `PUBLICATION_CHECKS_TOOLS` names a directory where `npm ci` installed the locked toolchain; they do not look on `PATH`. Copy `package.json` and `package-lock.json` from `actions/publication-checks` into an empty directory outside the repository, install the toolchain there with the command of the `commitlint` setup, and set `PUBLICATION_CHECKS_TOOLS` to that directory. `--userconfig /dev/null` keeps the user's npm configuration out of the install; on Windows, `NUL` takes the place of `/dev/null`. A local run needs a Node.js version within `engines.node` of the part's `package.json`; CI runs the version that `node.version` in the pins file pins:

  ```text
  npm ci --ignore-scripts --no-audit --no-fund --userconfig /dev/null --prefix <directory>
  ```

- Windows suites (`windows`, `etw-consumer-build`, `pinned-tools-windows`). Windows; the cases skip on other systems. The live ETW recording cases of `tests/test_windows_recording.py` also need `dotnet` with the .NET runtime that the ETW consumer's project names, and an account that may start the consumer's ETW session. Before they run, they start and stop that session once; when it cannot start, each of them skips with a reason that names the denied part. An elevated shell may start it, as in the `windows` job. Without elevation, an account needs three settings:

  - membership of Performance Log Users (`S-1-5-32-559`), which takes effect at the account's next log-on;
  - an allow entry with the mask `0x0081` on `Microsoft-Windows-Kernel-File` and on `Microsoft-Windows-Kernel-Process`;
  - an allow entry with the mask `0x0FF7` on SystemTraceProvider (`9e814aad-3204-11d2-9a82-006008a86939`).

  The account gains no administrator rights from them, but any process of the account may then trace these providers. [`etw_access.ps1`](etw_access.ps1) sets them up once, from an elevated PowerShell, for the account that runs it or for the account it names:

  ```text
  pwsh -NoProfile -File tests/etw_access.ps1 inspect [<account>]
  pwsh -NoProfile -File tests/etw_access.ps1 setup [<account>]
  pwsh -NoProfile -File tests/etw_access.ps1 restore [<account>]
  ```

  `inspect` lists the stored allow entries of the three providers and of the default descriptor with their account and mask, and the account's membership, and changes nothing. `setup` first records the stored descriptors of the three providers and the membership in `HKLM\SOFTWARE\SharedWorkflows\EtwAccess\<account SID>`, outside every checkout, and then gives the account the three settings; a repeated `setup` adds no duplicate entries and keeps the first record. `restore` writes the recorded descriptors back, removes a descriptor that was absent, removes the membership only when `setup` added it, and then removes the record; without a record it changes nothing. `restore` returns each of the three descriptors as a whole to its recorded state, so it also undoes any later entry on them, such as one that `setup` gave another account. A log-on after `setup` or `restore` brings the membership into effect. When an elevated prompt runs under another administrator account, `setup` and `restore` name the account that runs the tests.

- Python language step and Python floor (`python-language-step`, `python-floor`). The pinned ruff and mypy from the `python` tools of the pins file, in `HYGIENE_TOOLS` or on `PATH`, which `install_tools.py` installs with `--tool ruff --tool mypy`; the cases skip without them.

With these tools, the only cases that still skip are those that depend on the platform or the Python version.
